# 核心业务流程与订单状态机

> 本文档是核心业务流程与订单状态机的**全局唯一事实来源**,各域文件通过 `02-business-flows.md §小节` 文本引用,不复制此处内容。状态标记反映当前 `refactor/unify-module-structure` 分支工作区状态。

## 用户订购主流程

```text
浏览商品(首页/详情) → 加购物车或立即购买 → 确认订单(地址/配送时间/支付方式/备注)
→ 提交订单 → 微信支付 → 等待派单 → 配送中 → 送达即完成 → 评价
```

各环节现状:浏览商品/加购/下单/支付(已实现,G01 解决)/订单进度查看/配送跟踪(已实现)/送达即完成(已实现,R-ORD-11;2026-10 按行业惯例取消「待确认收货」中间态)/评价(已实现,G05 解决)。

## 订单状态机

订单共 **7 个状态**,三端共享同一状态模型(2026-10 按行业惯例修订:取消原「待确认收货」中间态,**非自提订单送达即完成**,自提当场完成):

| 状态 | 含义 | 用户端表现 | 送水工端表现 | 后台表现 |
| --- | --- | --- | --- | --- |
| 待支付 | 订单已创建,等待用户支付 | 显示"去支付" | 不可见 | 待支付列表 |
| 待派单 | 已支付,等待派单或抢单 | 显示"等待派单" | 「未接单」栏 | 可派单/查看 |
| 待配送 | 已接单/已派单,等待开始配送 | 显示"待配送" | 「已接单」栏 | 查看配送员 |
| 配送中 | 送水工已出发 | 可跟踪 | 「配送中」栏 | 查看配送进度 |
| 已完成 | 完成配送即完成(非自提送达即完成/自提当场完成) | 可评价/再次购买 | 计入业绩 | 核验照片/统计 |
| 已取消 | 未支付取消/支付超时/商家取消 | 显示已取消 | 不可见 | 查看原因 |
| 已退款 | 已支付订单取消并完成退款 | 显示已退款 | 不可见 | 查看退款信息 |

**状态流转表**(触发动作 → 前置状态 → 目标状态 → 触发方):

| 触发动作 | 前置状态 | 目标状态 | 触发方 | 说明 |
| --- | --- | --- | --- | --- |
| 创建订单(用户端) | — | 待支付 | 用户 | 已实现 |
| 支付成功回调 | 待支付 | 待派单 | 微信支付回调 | 记支付时间/交易号 |
| 支付超时(超时未支付) | 待支付 | 已取消 | 系统 | 自动取消并恢复库存 |
| 创建订单(送水工代客下单) | — | 待派单 | 送水工 | 免支付;自提则记录收款 |
| 用户取消(未支付) | 待支付 | 已取消 | 用户 | 恢复库存 |
| 用户取消/管理员取消(已支付) | 待派单 | 已取消 | 用户/管理员 | 生成退款申请(待审核,R-PAY-02) |
| 管理员派单(配送员在线) | 待派单 | 待配送 | 管理员 | 记派单时间(2026-10 与抢单口径统一:派单即「已接单/待配送」,送水工显式「开始配送」才进入「配送中」) |
| 送水工抢单 | 待派单 | 待配送 | 送水工 | 记录接单操作 |
| 开始配送 | 待配送 | 配送中 | 送水工 | 记出发时间 |
| 完成配送(拍照+收款方式,非自提) | 配送中 | 已完成 | 送水工 | 强制配送照片非空;记送达时间=完成时间;照片置「待核验」(G23);营收按完成时间即时计入(R-ORD-11) |
| 完成配送(拍照,自提) | 配送中 | 已完成 | 送水工 | 自提控制权当场转移,即时计入营收(R-ORD-09/11) |
| 退款审核通过 | 已取消(已支付) | 已退款 | 管理员 | 审核通过并退款成功后流转(已实现,R-PAY-02) |

> 规则引用:R-ORD-01 状态流转合法性、R-ORD-02 库存联动、R-ORD-03 取消规则、R-ORD-11 完成配送与营收确认、R-PAY-01 支付与退款(定义处见 04-order.md)。

## 派单与接单流程

订单进入「待派单」后,有两条履约路径:

```text
路径A(后台派单):管理员在订单详情选择在线送水工 → 派单成功 → 订单进入「待配送」(已接单)
路径B(抢单):送水工在任务页「未接单」栏看到订单 → 点击接单 → 订单进入「待配送」
```

- 派单要求送水工**在线**(已登录且状态为可接单);批量派单支持一次分配多单;
- 派单与抢单**目标态统一为「待配送/已接单」**(2026-10 修订,原派单直接置「配送中」与抢单口径不一致),由送水工显式「开始配送」才进入「配送中」;
- 抢单路径下,同一订单可被多个送水工看到,先到先得(幂等处理);
- 送水工端「未接单 / 已接单 / 配送中」三个栏目分别对应「待派单 / 待配送 / 配送中」状态。

## 配送履约流程

```text
开始配送(记录出发时间) → 送达 → 拍摄配送照片(必填,可多张) → 选择收款方式(现金/水票/扫码)
→ 提交完成 → 订单直接进入「已完成」(2026-10 按行业惯例:非自提送达即完成,自提当场完成)→ 生成操作记录时间线
→ 即时计入营收(按完成配送时间"送达时间")→ 用户可评价
```

- **拍照验证为硬性要求**:未上传照片不可完成配送,防止"未送即完成"与售后纠纷;
- 收款方式三选一:现金、水票、扫码收款;若订单为「自提」则无需现场收款;
- **完成配送与营收确认(R-ORD-11)**:2026-10 按行业惯例简化——**非自提订单完成配送即「已完成」并即时计入营收**(按送达时间归属),**自提订单控制权在取水当场转移**,同为完成即计入;取消原「待确认收货 + 送达 N 天自动确认」中间态(电商模型不适配送水"当面交付"场景),消除营收确认滞后与"业绩按送达/营收按确认"双口径;
- 送水工业绩/收款日报/对账按送达时间计入;
- 每一步状态变更均写入订单操作记录,用户端与后台可查看完整时间线。

## 收款与对账流程(跨两端)

```text
送水工当日完成订单 → 系统按收款方式预计算应收(现金/水票/扫码)
→ 送水工提交每日收款日报(填写三栏实际金额)
→ 与系统计算值比对:在容差内 → 正常提交;超容差 → 差异申诉状态
→ 管理员确认日报 → 按日执行对账(自动匹配/标记差异)→ 管理员审核 → 完成
```

- 日报状态:`草稿 → 已提交 → 已确认`,超容差/水票不符进入 `有争议`(2026-08-24:后端 `submitDailyCollection` 超容差置 `DISPUTED`,差异口径=填报现金+扫码 vs 系统计算现金+扫码,见 06-collection.md §域内业务规则);
- 对账状态:`待对账 → 匹配/有差异 → 已复核`(界面统一文案,对应枚举 PENDING/MATCHED/DISCREPANCY/REVIEWED,见 06-collection.md §R-COL-03);
- 对账记录在送水工端「对账记录」页可见,状态变更全程留痕。

## 支付与退款流程 [已实现]

**支付**:用户提交订单 → 订单进入「待支付」→ 发起微信支付(JSAPI 预支付)→ 微信支付回调通知 → 验签/金额校验/幂等(R-PAY-01)→ 订单进入「待派单」;未支付超时由延迟消息主触发 + 调度器兜底,自动取消并恢复库存(R-ORD-04)。

**退款**:用户/管理员取消已支付订单 → 生成退款申请(待审核)→ 管理员审核通过 → 微信退款 → 退款完成;审核拒绝则退款终止。退款状态:待审核 → 已通过/已拒绝 → 已完成/失败。

> 现状(2026-08,G01 已解决):`PaymentServiceImpl` 为真实实现(微信支付 V3 JSAPI 预支付 + 假支付模式 `wechat.pay.mock-enabled` 供开发/测试);`WechatPayNotifyController` 提供 `/api/pay/notify` 回调端点(验签/金额校验/幂等);超时取消由 `PAYMENT_EXPIRY_CHECK` 延迟消息主触发 + `PaymentExpiryScheduler` 兜底扫描,幂等与互斥由 `payments.version` 乐观锁 CAS 保证;`refund()` 退款并落 `payment_refunds`(status=COMPLETED,退款/净营收统计口径);管理员退款审核流(R-PAY-02)与后台退款管理页已落地(2026-08-19)。规则定义见 04-order.md §R-PAY-01/02。

## 代客下单流程

送水工在送水工端为不便自助下单的用户(如老年人、电话订水)代下单:

```text
送水工选择商品 → 选择用户地址 → 填数量 → 选择是否自提 → 提交 → 订单进入「待派单」
```

与用户自下单的差异:免去在线支付环节(现金/水票结算);「自提」订单记录为已收款(水钱已收/水票已扣),用户到店取水。

## 订单计价与熟客分组价

订单金额 = 成交单价 × 数量,成交单价按以下优先级解析(R-MKT-01,定义于 10-marketing.md §2):

```text
① 送水工代客下单手动填写的实收单价(若有)
② 下单用户所属客户分组的商品专属价(熟客价,若有)
③ 商品目录价(product.price)
```

- 金额一律以分计算、服务端计算与校验(R-MON-01),用户端与送水工端不传价格,防篡改;
- 自动应用(已实现 2026-08):用户自助下单与代客下单均按 ②③ 解析;用户端商品详情/确认订单页按登录用户展示熟客价——成交单价 `effectivePriceCents`、是否命中 `hasGroupPrice`、来源标签 `priceSource` 由 client 按登录用户解析(未登录回退目录价),G52 已解决;
- 手动兜底:代客下单时送水工可修改实收单价(①),订单记录成交单价留痕;订单归属须为收货地址所属客户方可按客户解析(G51 已解决,2026-08);
- 价格策略配置见 10-marketing.md §F-MKT-002;客户分组管理见 §F-MKT-001(均已实现 2026-08,G50 已实现);
- 营销玩法扩展(优惠券、满减/折扣、限时特价、会员折扣)见 10-marketing.md §2.2~2.7(R-MKT-02~07):成交单价解析扩展为「手动实收价 → 分组价 → 限时特价 → 目录价」,订单层按「满减/折扣 → 会员折扣 → 优惠券」叠加,订单计价为本链路的应用层。

## 复购、周期订购与套餐卡流程 [2026-10 新增]

```text
一键复购:历史订单 → 「再来一单」→ 商品按当前在售/价格重算(缺货剔除)→ 确认订单页 → 提交(R-ORD-06 幂等)
周期订购:创建计划(商品/周期/时段/地址)→ 到期自动生成「待支付」订单(幂等:计划 id+期次)→ 推送提醒 → 支付/超时(R-ORD-04)
套餐卡:购买(微信支付,既有 F-ORD-005 链路)→ 按张数/桶数生成卡记录 → 下单核销抵扣(幂等)→ 未核销可退(对齐 R-MKT-08)
```

- **一键复购(R-ORD-12/F-ORD-025)**:以历史订单商品明细为模板重建待下单数据,价格按 R-MKT-02 于提交时重算,不复用历史成交价与优惠/押金状态;失效商品剔除并提示。
- **周期订购(R-ORD-13/F-ORD-026)**:每次执行生成独立正常订单,走既有支付/超时/取消/评价链路;同期次幂等仅生成一单;自动下单失败转提醒(F-NTF-007)不静默。
- **套餐卡(R-MKT-11/F-MKT-010)**:核销/退款口径对齐水票(R-MKT-08);**用户储值不做**(2026-10-09 合规决策:无预付卡资质,余额充值/余额支付/余额抵扣/组合支付均不实现,见 10-marketing.md §1.1)。
- **会员与积分(R-MKT-12/13)**:会员等级按累计消费自动升降、权益自动应用;积分随订单完成获取、退款回退,可兑换与抵扣。

## 企业客户、转单与工资结算流程 [2026-10 新增]

```text
企业客户:后台建客户档案(账期/信用额度)→ 多地址批量下单 → 按收货地址拆单 → 月结订单不即时收款(计入应收账款)→ 账期账单 → 收款核销 → 集中开票
转单:送水工发起转单 → 目标送水工接收(或管理员指派)→ 订单归属转移 → 原任务移除/新任务新增(全程留痕)
工资结算:选周期 → 按规则汇总(底薪 + 计件提成 + 补贴 − 扣款)→ 生成结算单(同周期同人唯一)→ 复核确认 → 发放(幂等、留痕)
水票核销(修订):购票 → 持有 → 核销(现状下单侧抵扣 / 目标送达侧扫码,每票唯一票号防重)→ 退回票夹/过期
```

- **企业客户(R-ORD-14/F-ORD-027,月结资金类)**:批量下单按收货地址拆为多张子订单,各子订单独立走库存校验(R-ORD-02)与状态机(R-ORD-01);月结订单生成应收账款、按账期生成账单并与开票联动(退款红冲);信用额度「已用 + 本单 ≤ 上限」校验,超额拦截。
- **转单(R-ORD-15/F-ORD-028)**:仅「待配送/配送中」订单可转,目标须在线且可接单(R-ORD-08),接收后订单归属转移并留痕;拒绝/超时回退原送水工;收款归属与转单次数上限为开放问题。
- **工资结算(R-COL-05/F-COL-012,资金类)**:计件口径与已完成订单、日报对账一致(R-ORD-11/R-COL-03);同周期同人唯一 + 发放幂等防重复发放;差异/负值告警(资损监控),发放记录留痕可核对。
- **水票核销点位(R-MKT-08 修订)**:现状核销发生在用户下单侧(下单即抵扣,订单创建同事务原子核销);每张票有**全局唯一票号**(`user_tickets.ticket_no` 唯一索引 + 按月原子取号),核销为**原子条件更新 + 幂等**(2026-10 代码核验**已具备**),订单取消退回票夹(RETURNED)可复用;目标增强为**送达侧扫码核销**(见 14-misc.md §G91)。
